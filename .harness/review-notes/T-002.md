### 成立，記為 finding（皆 non-blocking for T-002）

**F-01（non-blocking，源自 AC-1）`launch.js` 固定 1.5 秒延遲後開瀏覽器，不等 server ready。**
實測：另起一隻無關 node 程序佔用 3100（PID 27300），再跑 `start-hub.cmd` → 3100 擁有者仍是 27300、Hub 的 `src/server.js` 程序完全不存在，但 `launch.js` 仍會在 1.5 秒後開瀏覽器指向 `http://127.0.0.1:3100/`，使用者看到的是別人的頁面（本次看到 `SQUATTER-ON-3100`）。前景跑 `node src\server.js` 可見 `Error: listen EADDRINUSE ... port 3100`、exit 1，但 `launch.js` 用 `stdio: 'ignore'` 把它吞掉。
影響：AC-1「單一入口開啟可操作介面」在 3100 被占用時不成立——使用者得到死頁而非錯誤訊息。
不在 T-002 範圍內修復的理由：AC-1 正常情境已由實測證明（HTTP 200 + title `MCP Hub` + API 回報真實狀態）；此為失敗情境的診斷品質，屬 T-007「狀態與診斷」的範圍。建議記入 T-007。

**F-02（non-blocking，源自 AC-2 Gap 2）`unknown` 狀態在 UI 中不顯示為紅色錯誤。**
`public/index.html` 的 CSS 只為 `data-state="running"`（綠）、`"stopped"`（灰）、`"error"`（紅）上色；`app.js` 的 `STATE_TEXT` 沒有 `unknown` 的錯誤樣式以外的呈現。`parseStatus` 對未識別 exit code 或 timeout 回 `unknown`，此時 `stop()` 會正確回 error（`after.state !== 'stopped'`），但單純 `status()` 查詢會顯示灰色「Gateway 狀態未知」。

**F-03（non-blocking，源自 AC-5 Gap 3）管理 API 無認證、無 Origin 檢查。**
實測：帶 `Origin: https://evil.example.com` 對 `POST /api/gateway/start` 發出無憑證請求 → HTTP 200、`state=running`（Gateway 確實被啟動）；`GET /api/gateway/status` 同樣 200。瀏覽器 same-origin 政策會擋掉跨源**讀取回應**，但 `fetch` 的 simple POST（`Content-Type` 為 text/plain 等）仍會送出，因此惡意網頁可以停止／重啟 Gateway，只是讀不到結果。
PLAN-5 未把管理頁認證列入 V1 範圍，PLAN-6 亦未列；此為已知威脅模型限制，非規格違反。建議記入文件。

**F-04（non-blocking）跨使用者本機存取未測。**
綁 127.0.0.1 代表同機任何使用者（含其他帳號的程序）都能呼叫管理 API。本機為單一使用者環境，未以 `runas` 實測。

### AC-5 的 iPhone 一側仍為 UNVERIFIED

`tailscale serve status` 與 `tailscale funnel status` 目前皆只列一條規則：`https://alvin.tail63d20f.ts.net (tailnet only) |-- /mcp proxy http://127.0.0.1:3050/mcp`。3100 從未出現在 serve proxy 中，因此 iPhone 沒有任何到達管理頁的路徑。WSL 節點 alvin-1（100.79.209.7）實測 `http://100.119.224.46:3100/` → curl 000。

4. 人工測試期間曾短寫壞 `server.pid` 以製造 AC-4 情境，並曾殺掉 3051 的 http 下游以測下游失效；兩者皆已恢復。收尾後 `python -B tests/acceptance/check.py --ticket T-002` 重跑通過（36.3s），兩服務經 Gateway 皆回正確結果。
5. UI 僅有 Gateway 控制（啟動／停止／重啟 + 狀態文字）。`check.py` 中 T-003 起的 `新增 MCP Server`、`儲存並套用`、服務列表、編輯／停用／刪除、連線檢查、日誌面板**在本建置中不存在**；`check_002` 不觸碰這些控制，故 T-002 驗證通過，但 T-003 之後的 AT 步驟會失敗。
